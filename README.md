# 포트폴리오 — 조남두

AI 코딩 에이전트로 만든 서비스와, 그 결과물을 신뢰하기 위해 만든 절차.

세 프로젝트는 따로 있는 것이 아니라 하나의 순서입니다.
먼저 **AI가 만든 코드를 검증하는 절차**를 도구로 만들었고, 그 절차 위에서 **서비스 두 개**를
만들어 운영하고 있습니다.

```
agent-flow  ──(이 절차로)──>  aitrading        자동매매 봇 (운영 중)
                        └──>  trading-journal  거래일지 웹 (운영 중)
```

| 프로젝트 | 무엇 | 규모 | 코드 |
|---|---|---|---|
| [agent-flow](case-studies/agent-flow.md) | AI 개발 워크플로 CLI + 검증 게이트 | Python 31,801줄 · 커밋 425 | [GitHub](https://github.com/chonamdoo/agent-flow) |
| [aitrading](case-studies/aitrading.md) | Bybit 선물 자동매매 봇 | Python 53,226줄 · 테스트 1,215개 · 커밋 428 | 비공개 (실거래 전략·키) |
| [trading-journal](case-studies/trading-journal.md) | 크립토 선물 거래일지 | TypeScript 27,377줄 · 커밋 156 | [GitHub](https://github.com/chonamdoo/trading-journal) |

## 왜 절차부터 만들었나

AI 코딩 도구를 실무에 붙이면서 반복해서 부딪힌 문제가 셋이었습니다.

1. **산출물은 나오는데 검증이 안 된다.** "테스트를 작성했습니다"라고 보고하지만 실제로
   실행됐는지 알 수 없습니다.
2. **대화가 길어지면 요구사항이 증발한다.** 초반에 지시한 값이 컨텍스트 압축 과정에서
   사라지고, 구현 단계에서는 이미 다른 것이 만들어져 있습니다.
3. **에이전트가 범위를 조용히 늘린다.** 요구하지 않은 리팩터링·모듈 분리·성능 최적화가
   섞여 들어옵니다.

셋 다 프롬프트를 개선하는 방식으로는 해결되지 않았습니다. 개인이 잘 쓰는 요령이 아니라
**절차 자체를 고정해야 하는 문제**였습니다. 그래서 도구를 먼저 만들었습니다.

## 검증 체계의 핵심 네 가지

`agent-flow`가 실제로 하는 일입니다. 자세한 내용은 [케이스 스터디](case-studies/agent-flow.md)에 있습니다.

**판정 권한을 에이전트에서 떼어낸다.**
워크플로 YAML은 단계 *정의*일 뿐이고, 다음 단계를 결정하는 것은 런너입니다. 에이전트는
런너가 출력한 `next_command`를 따라야 하며 스스로 단계를 건너뛸 수 없습니다.

**주장이 아니라 관찰로 판정한다.**
TDD의 red 단계에서 테스트를 실제로 돌렸는지는 에이전트의 보고가 아니라 `PostToolUse` 훅이
기록한 명령 실행 로그로 판정합니다. 마커에 무엇을 적든 런너가 로그를 직접 읽습니다.
첫 실행에서 통과한 테스트는 red 단계가 아닙니다.

**요구사항마다 검증 방식을 하나씩 붙인다.**
사용자의 모든 지시를 순번이 매겨진 원장으로 기록하고 각 항목에 검증 방식을 붙입니다
(`test:<name>` / `symbol:<symbol>=<value>` / `manual`). 리뷰어가 approve해도 미충족 항목이
있으면 단계가 완료되지 않습니다.

**같은 세션이 만든 코드를 같은 세션이 리뷰하지 못하게 한다.**
구현 리뷰와 아키텍처 리뷰 모두 독립된 서브에이전트 2개 이상이 나눠서 수행하고,
`reviewer-source: sub-agent` 기록을 요구합니다. 한 명이라도 `request-changes`면 전체가
`request-changes`입니다.

## 이 절차로 실제 무엇을 만들었나

**[aitrading](case-studies/aitrading.md)** — Bybit USDT-perp 선물 자동매매 봇.
차트 패턴 + CCI 다이버전스 기반 진입, Clean Architecture 4계층, ADR 15건,
테스트 함수 1,215개. Docker + GHCR로 도쿄 리전 서버에 배포해 운영 중입니다.
자동 배포를 의도적으로 두지 않았습니다 — 진행 중인 포지션이 있으면 배포를 보류합니다.

**[trading-journal](case-studies/trading-journal.md)** — 크립토 선물 거래일지 웹 서비스.
Next.js App Router + Supabase, API 라우트 50개, 테스트 135개. 거래소 5종 API 연동,
거래소 키는 AES-256-GCM으로 암호화하고 키 링 회전을 지원합니다.
14개 테이블 전부 RLS를 적용했고 정책은 46개입니다. Vercel에서 운영 중입니다.

## 지금 남은 문제

`agent-flow`는 아직 **개인 도구**입니다. 혼자 쓰는 절차를 만드는 것과, 조직이 함께
합의하고 신뢰하는 절차를 만드는 것은 다른 문제입니다. 후자는 아직 풀지 못했습니다.

풀리지 않은 것은 넷입니다.

- **검증 기준을 조직이 합의하는 절차** — 마커 목록을 누가 정하고 어떻게 바꾸는가.
  지금은 제가 정했기 때문에 제게만 맞습니다.
- **팀원마다 다른 숙련도** — 절차를 이해하고 쓰는 사람과, 막히는 지점에서 우회로를 찾는
  사람에게 같은 게이트가 같은 의미인지 확인하지 못했습니다.
- **절차가 만드는 마찰과 얻는 신뢰의 손익 분기점** — 게이트가 많아 혼자 쓸 땐 감당되지만,
  팀에 넣으면 "왜 이렇게 오래 걸리냐"는 반발이 먼저 올 것입니다. 어디까지가 지불할 만한
  마찰인지 기준이 없습니다.
- **리뷰 서브에이전트 비용의 경제성** — 리뷰어를 병렬로 띄우면 토큰 비용이 배로 늘어납니다.
  팀 규모로 곱해졌을 때의 손익을 계산해 본 적이 없습니다.

앞의 셋은 기술 문제가 아니라 사람과 조직의 문제입니다. 자동화를 늘리는 일이 곧 신뢰를
얻는 일은 아니라는 것이, 이 도구를 쓰면서 가장 분명해진 것입니다.
