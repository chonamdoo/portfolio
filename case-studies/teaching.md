## 왜 만들었나

`agent-flow`의 검사 단계는 제게 맞춰 설계돼 있습니다. `required_markers`가 무슨 뜻인지 알고,
왜 red 단계에서 테스트가 실패해야 하는지 아는 사람에게만 작동합니다. 그 전제를 걷어내고
같은 원리를 전달하려면 어휘부터 바꿔야 했습니다.

## 강의 슬라이드 37장

![강의 표지](../assets/lecture-vibecoding-01.png)

대상은 앱 아이디어는 있지만 개발자가 아닌 사람입니다. PRD, 코드리뷰, CI/CD를 다룹니다.

### 문제를 예시로 먼저 보여준다

| 기획서 | 코드 | 결과 |
|---|---|---|
| 할인 코드는 결제 대행사와 연동되어야 한다 | DB에 할인 코드만 저장했다 | 사용자가 입력해도 할인이 적용되지 않는다 |

화면만 보면 동작하는 것처럼 보이고, 코드만 봐도 잡기 어렵습니다. 기획서와 코드를 대조해야
드러납니다.

### 전달한 도구 넷

**PRD 계층** — Requirement → Feature → Spec → Userflow. "쉽게 로그인하는 예쁜 가계부 앱"이
왜 나쁜 지시인지를 `R1 / F1 / S1 / U1` 형태와 나란히 놓고 비교합니다. 완료 기준이 있어야
리뷰 기준으로 쓸 수 있습니다.

**작업 단위** — 화면 하나, 기능 하나, 검증 하나. 순서는 PRD 읽기 → 목표 고르기 → 구현 →
Spec 대조 → 커밋입니다. 프롬프트에도 범위를 못박게 합니다 — `PRD의 F1 기능만 구현해줘.
다른 기능은 만들지 말고, 어떤 Spec이 충족됐는지 알려줘.`

**GAP 리포트** — Spec별로 구현 상태와 위험도, 다음 액션을 표로 만듭니다.

| Spec | 상태 | 위험도 | 다음 액션 |
|---|---|---|---|
| S1 금액은 0보다 커야 한다 | 구현됨 | 낮음 | 없음 |
| S2 날짜가 없으면 오늘 날짜 | 일부 구현 | minor | 빈 날짜 테스트 추가 |
| S3 결제 성공 후 권한 부여 | 미구현 | major | webhook과 DB 상태 연결 |

**심각도와 자동화 규칙** — critical / major / minor / nit 네 단계를 정하고, 각 단계에서 자동화가
무엇을 하는지 연결합니다.

| 결과 | 자동화 |
|---|---|
| critical 또는 major 있음 | 자동 승인 금지, 사람 리뷰 필수 |
| minor만 있음 | 승인 가능, 머지는 보류 |
| nit만 있음 | 팀이 허용하면 자동 머지 가능 |

리뷰 결과를 사람의 판단에 맡기지 않고 자동화 규칙으로 바꾸는 부분이 `agent-flow`와 같습니다.

`prd-code-reviewer` 스킬 초안도 함께 넣었습니다. PRD와 PR diff를 비교해 누락·버그·보안
문제를 찾고, 판정과 심각도 집계, PRD 대조 결과, 다음 액션을 출력하는 구성입니다.

## 여기서 배운 것

`agent-flow`의 한계로 적어둔 "팀원마다 다른 숙련도" 문제를 여기서 먼저 만났습니다.

- **어휘가 장벽이다** — `required_markers`는 안 통하고 "완료 기준"은 통합니다. 개념이
  어려운 게 아니라 이름이 막습니다
- **판정 기준을 먼저 합의해야 한다** — 심각도 단계를 정하지 않으면 리뷰 결과로 아무것도
  못 합니다. 어느 단계부터 사람이 멈출지가 곧 자동화의 계약입니다
- **규율을 요구하면 실패한다** — 검증을 사람이 기억해서 실행하게 두면 안 하게 됩니다.
  절차의 기본값으로 넣어야 실행됩니다. `agent-flow`가 훅으로 관찰하는 이유와 같습니다

다만 이건 일방향 전달입니다. 제가 정한 기준을 전하는 자리였고, 서로 다른 기준을 가진
사람들이 하나로 합의하는 과정은 아니었습니다. `agent-flow`에 남은 문제가 그것입니다.
